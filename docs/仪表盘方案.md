## 二、指标采集方式（已在本机实测可用，不引入新依赖）

| 指标 | 采集方式 | 实测 | 限制 |
|---|---|---|---|
| GPU 占用 | `ioreg -r -d 1 -w 0 -c AGXAccelerator` → `Device Utilization %` | ✅ 取到 79% | **系统级**，含浏览器等其他程序，不是本任务独占 |
| GPU 显存 | 同上 → `In use system memory` | ✅ 1.4 GB | 同上 |
| 内存 | `vm_stat` + `memory_pressure` | ✅ 16 GB 总量、可用页 | — |
| 磁盘 | `df -h` | ✅ 剩余 10 GB（**已用 95%**） | — |
| 进程 CPU/内存 | `ps -o %cpu,rss,etime -p <pid>` | ⚠️ MCode 沙箱里 EPERM，**用户终端里正常** | 需降级 |
| 总体 CPU | `top -l 1 -n 0` | ⚠️ 同上 | 需降级 |
| CPU 温度/散热 | `pmset -g therm` | ❌ SMC 权限失败 | **不可用**，不做 |
| 进程存活判断 | `os.kill(pid, 0)`（纯 Python） | ✅ 可用 | 用于清理残留状态文件 |

结论：**除温度外都能拿到**。`psutil` 没装，也不想为了看板引入编译依赖
（Mac 上装 psutil 偶尔要编译，setup.sh 阶段已经踩过 uv 装包失败的坑）。

## 三、方案

### 3.1 作业状态：从内存改成文件（关键改动）

新增 `output/_status/<slug>.json`，任何进程（网页服务、命令行脚本）都能写，仪表盘统一读：

```json
{
  "id": "20261021 上午闫树",
  "kind": "polish",
  "doc_id": "20261021 上午闫树",
  "stage": "polishing",
  "message": "minimax 润色中",
  "done": 480,
  "total": 2157,
  "pid": 85749,
  "source": "cli",
  "started_at": 1792951877,
  "updated_at": 1792951900,
  "finished_at": null
}
```

- `output/` 已在 `.gitignore`，不会进 Git ✅
- 写入时机：作业开始创建 → 每批落盘更新 done/total → 结束写 `finished_at`
- **残留文件**：仪表盘用 `os.kill(pid, 0)` 判断进程是否还活着；进程已死但文件没写结束 → 标成「异常退出」而不是「运行中」

### 3.2 新增 `app/monitor.py`

- 一个后台线程每 2 秒刷新一次系统指标，缓存到内存
- 采集全部走 macOS 内建命令（`subprocess` + 超时保护），任何一项失败就返回 `null`，**不拖垮接口**
- 同一个进程内共享（服务是多线程的，别每次请求都 fork 一堆命令）

## 四、风险与降级

| 风险 | 处理 |
|---|---|
| `ps`/`top` 在某些环境被禁（如 MCode 沙箱） | 采集失败就返回 `null`，界面显示「—」，**绝不让看板把服务搞挂** |
| `ioreg` 在未来 macOS 版本改名 | 采集失败同样降级为 `null` |
| 状态文件残留 | `os.kill(pid,0)` 判存活 + 按 `updated_at` 超时（如 10 分钟没更新）双保险 |
| 多进程同时写同一篇 | 状态文件名带 pid，避免互相覆盖 |
| 采集本身有开销 | 后台线程 2 秒刷新 + 缓存；`top -l 1` 本身要 1 秒，所以不能每次请求都采集 |
| 磁盘只剩 10GB（已用 95%） | 看板会显示磁盘水位，正好用来提示；长期要清理 `output/_backup_*` |
