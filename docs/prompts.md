# 提示词清单（从代码反推）

本文档把项目里**实际发给模型的提示词**逐条反推出来。提示词本身硬编码在 `app/llm.py`
的常量里，这里原样记录，方便对照排查、调参，以及判断某次改写为什么不满意。

> 约定：代码位置用 `app/llm.py:行号` 标注；`{占位符}` 是运行时拼进去的内容。

---

## 总览

| # | 环节 | 系统提示词 | 触发时机 | temperature | max_tokens |
|---|---|---|---|---|---|
| 1 | 逐条润色 | `POLISH_SYSTEM` | 每批段落 | 0.25 | `批次条数 × 320 + 16384` |
| 1b | 润色·备用格式 | `POLISH_SYSTEM_FALLBACK` | 主格式没返回内容时 | 0.25 | 同上 |
| 2 | 知识库·分块提炼 | `CHUNK_SYSTEM` | 每 2600 字一块 | 0.2 | `1400 + 16384` |
| 3 | 知识库·合并去重 | `CHUNK_SYSTEM` | 合并后仍超长时 | 0.2 | `2600 + 16384` |
| 4 | 知识库·结构化汇总 | `KB_SYSTEM` | 每篇一次 | 0.2 | `max(8192, 16384)` |
| 5 | 连通性探测 | 临时字符串 | 「检测后端可用」 | 0.1 | 16 |

`16384` 来自 `STT_LLM_API_MAX_TOKENS`（`app/config.py:43`），是给推理模型（M2/M3 系列）
预留的**思考预算**。给小了 `finish_reason=length` 会把正文一起砍没——这是踩过的坑。

---

## 1. 逐条润色

**系统提示词** `POLISH_SYSTEM`（`app/llm.py:23`）：

```
你是一名中文文稿编辑。你会收到一段演讲的原始转写文本，需要你把它整理成书面稿。

严格要求：
1. 只做纠错与润色，不得增加原文没有的信息，不得改变讲者的观点、数字和结论。
2. 修正同音字、错别字、专有名词错误（结合上下文判断；中文数字年份/百分比/数量要转成阿拉伯数字，如"二零二五年"→"2025年"；英文专有名词按通行写法，如 "R and D" → "R&D"）。
3. 去掉口语表达：语气词（嗯、呃、啊、那个、然后就是）、口头禅、重复、自我修正的痕迹。
4. 保留讲者原始的段落意图，但允许合并碎句、补全标点，使句子通顺可读。
5. 保留其中的专业术语、产品名、人名、地名，不要意译或改写专有名词。
6. 严格保持条目数量与顺序：输入 N 条就必须输出 N 条，序号一一对应，不得遗漏、合并、拆分或新增。
7. 四位年份必须完整保留：像"二零二零年""二零二二年"这类中文数字年份，转成阿拉伯数字时必须是 2020年、2022年，
   不能写成"二零年"（丢位），也不能写成"2020-20年"。原文里的所有数字、百分比、金额、日期、编号一律不得改动或省略。

输出格式（严格遵守）：每行一个 JSON 对象，不要加任何其他文字或代码块标记：
{"i": 输入序号, "t": "改写后的文本"}
```

**用户提示词**（`app/llm.py:570`，运行时拼装）：

```
{上文提要}请逐条改写下面 {N} 条转写文本，严格保持 {N} 条、顺序与序号不变。

1. {第 1 条规整稿}
2. {第 2 条规整稿}
...
{N}. {第 N 条规整稿}
```

- 「上文提要」只在非首批次出现：取同组前 3 段的规整稿，截到 400 字。
- 条目里的文本是 `textproc.clean_text(raw)` 的结果（口语已清理），不是原始转写稿。

**备用格式** `POLISH_SYSTEM_FALLBACK`（`app/llm.py:40`）：与主提示词只有输出格式一句不同，
把 JSON 行要求换成纯文本编号格式——部分模型对这个更听话。

```
输出格式（严格遵守）：每行一条，格式为「序号. 改写后的文本」，序号从 1 开始连续递增，不得遗漏或合并。
```

**实际请求长什么样**（已脱敏的真实请求）：

```
system: 你是一名中文文稿编辑。…
user:   请逐条改写下面 3 条转写文本，严格保持 3 条、顺序与序号不变。

        45. 二零二零年八月份，欧元发布了关于深入实施人工智能加行动的意见。
        819. 直到二零二二年十二月的一个很重磅的一个制度，就是数据二十条。
        1044. 它第一次出现是在二零二零年，是在十四五规划里面啊。
```

> **注意序号**：提示词里的编号是**段落在本批中的绝对位置**（`i + 1`），模型会原样回填。
> 解析时必须按这个编号取值——早前取值用的是「批内相对位置」，两者在第 2 批往后对不上号，
> 导致模型的改写被整批丢弃（提交 `543b8ed` 修的就是这个）。

**返回解析**（`app/llm.py:_parse_indexed`）按优先级尝试三种格式：

1. 整个 JSON 数组 `[{"i":1,"t":"…"}]`
2. JSON 行（每行一个对象，允许行尾夹思考文字、允许单个对象被截断）
3. 纯文本 `1. xxx` 编号格式

拿到之后还要过三道守卫，任一不过就退回规整稿：

| 守卫 | 拦什么 | 判据 |
|---|---|---|
| 条目对齐 | 改写跑偏/错位 | 与原文字符相似度 ≥ 0.45 |
| 数字保真 | 年份被读丢 | 年份按**数值**比（`二零二零` ↔ `2020` 等价）；其余数字比**字符总量** |
| 不加戏 | 自行补出原文没有的人名 | 知识库专名集合整体比对（`_kb_adds_names`） |

## 2. 知识库（两段式）

长稿不做一次性提炼，先按 2600 字切块逐块提炼要点，再合并去重，最后按固定结构输出。

### 2.1 分块提炼

**系统提示词** `CHUNK_SYSTEM`（`app/llm.py:872`）：

```
你是一名中文文稿编辑。你会收到一段演讲稿的中间部分，请提取其中值得保留的信息。

输出要点，每行一条，不要标题、不要解释：
- （事实、数据、观点、案例、结论；保留具体数字与人名地名）
```

**用户提示词**（`app/llm.py:931`）：

```
这是演讲稿的{第 3/50 部分}：

{这一块的正文}
```

被内容审核拦下时（HTTP 422 `new_sensitive`），把这一块**切成两半各试一次**
（`app/llm.py:944`），能救一半算一半。

### 2.2 合并去重

合并后超过 9000 字才走这一步（`app/llm.py:989`）：

```
system: 你是一名中文文稿编辑。…（同 CHUNK_SYSTEM）
user:   以下是演讲稿各部分的要点，请去重合并：

        {各块要点拼起来的内容}
```

### 2.3 结构化汇总

**系统提示词** `KB_SYSTEM`（`app/llm.py:45`）：

```
你是一名内容编辑。你会收到一段演讲的整理稿，请提炼成结构化的知识库资料。

输出严格使用以下 Markdown 结构，不要有多余说明：
# 标题
## 摘要
（3-5 句话概括核心观点）
## 要点
- （逐条列出，每条一句话）
## 术语表
- 术语：解释
## 待确认
- （原文含糊或存疑的点，没有则写"无"）

篇幅要求：要点不超过 30 条，术语表不超过 15 条。必须完整输出全部 5 个小节，
不要在最后一句中途停下（前面写太多导致「术语表」「待确认」写不完）。

只提炼原文里真实出现的内容，不得补充原文没有的信息：
- 原文说"总书记"就写"总书记"，不要自行补全成具体人名；反之亦然
- 不要添加原文没有的引语、出处、数字或结论
- 原文含糊的地方写进「待确认」，不要靠常识补全
```

**用户提示词**（`app/llm.py:1000`）：

```
标题：{文档标题}

以下是演讲整理稿及要点提炼，请产出结构化的知识库资料。

【整理稿】
{全文前 6000 字}

【要点提炼】
{各块要点合并后的内容}
```

**重试时追加的要求**（`app/llm.py:1018`，首次输出不完整才追加）：

```
注意：上一次输出被截断或缺少小节。请务必输出全部 5 个小节
（标题/摘要/要点/术语表/待确认），要点控制在 25 条以内、术语表 10 条以内，
务必以「## 待确认」小节结尾。
另外只写原文里真实出现过的人名与称谓，不要自行补全。
```

**兜底**：两次都不合格就补空节，保证 `## 摘要 / ## 要点 / ## 术语表 / ## 待确认`
四节一定在（`_kb_complete` 判定，`app/llm.py:880`）。

> 这里的「4 节 + 标题」就是验收脚本 `verify_all.py` 查的结构。

## 3. 连通性探测

界面点「检测后端」时发一次极短请求（`app/llm.py:486`）：

```
system: 只回复「好的」两个字。
user:   回复两个字：好的
```

参数 `max_tokens=16, temperature=0.1`。只验证「能不能连通 + 模型在不在」，不做质量判断。

---

## 4. 提示词之外的约束（提示词管不到的）

有几类错误模型自己意识不到，靠提示词压不住，是在**代码层**兜住的。改提示词前先看这里：

| 现象 | 在哪拦的 | 提交 |
|---|---|---|
| 规整阶段把年份压掉一位（`二零二零年`→`二零年`） | `textproc.strip_stutter` 豁免两位以上中文数字串 | `79213c0` |
| 模型改写时把年份读丢 | `_numbers_preserved`（按数值）+ `_digits_intact`（按字符量） | `6b4af38` |
| 模型只写出一部分条目就静默收工 | `polish_segments` 拆小重试 + `finish_reason=length` 日志 | `543b8ed` |
| 模型的改写整批丢失 | 取值改为按模型回填的绝对编号 | `543b8ed` |
| 知识库自行补人名 | `_kb_adds_names` 专名集合比对 | `62e72f8` |
| 知识库被 max_tokens 截断、缺小节 | `_kb_complete` + 重试 + 补空节 | `efab49c` |
| 推理模型把思考过程写进正文 | `_strip_think` 剥 `<think>…</think>` | `6687df0` |

## 5. 调参入口

| 环境变量 | 默认 | 作用 |
|---|---|---|
| `STT_LLM_BACKEND` | `local` | `minimax` / `deepseek` / `openai` 等，或自定义 OpenAI 兼容地址 |
| `STT_LLM_MODEL` | `mlx-community/Qwen3-8B-4bit` | 本地模型名（在线后端由界面里填的模型名优先） |
| `STT_LLM_API_MAX_TOKENS` | `16384` | 推理模型的思考预算余量 |
| `STT_LLM_API_TIMEOUT` | `600` | 单次调用超时（秒），推理模型单次要几分钟 |
| `STT_LLM_API_RETRIES` | `3` | 失败重试次数（429/503 会长退避） |

批量大小不在环境变量里，代码里两处：

- `polish_segments(batch_size=16, max_chars=2200)` — 一批 16 条或 2200 字，先到先切。
  **定向重刷（跨全篇挑的零散段落）会改用 4 条一批**：条目越零散模型想得越多，
  实测 12 条一批时思考 token 冲到 20220、`max_tokens=20224` 被吃光，正文一个字没有。
- `build_knowledge_base(size=2600)` — 知识库切块大小。

## 6. 想改提示词时

1. 提示词常量在 `app/llm.py` 顶部（`POLISH_SYSTEM` / `KB_SYSTEM` / `CHUNK_SYSTEM`）。
2. 改完至少跑一遍：
   ```bash
   .venv/bin/python scripts/test_llm_output.py     # 思考块剥离 + JSON 解析
   .venv/bin/python scripts/test_kb_guard.py        # 知识库截断重试 + 补节
   .venv/bin/python scripts/test_polish_batch.py   # 批次映射 + 缺条目重试
   .venv/bin/python scripts/test_textproc_numbers.py
   ```
3. 真实效果得用真实数据看：改一段 → 用 `scripts/_local_repolish.py "<文档名>"`
   重刷该篇 → `scripts/verify_all.py` 验收 → `scripts/scan_numbers.py` 体检数字。
